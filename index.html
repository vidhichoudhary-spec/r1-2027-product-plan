How the backlog works

Both the Vendors and Vendor Marketplace teams work from a single ranked backlog via shared Jira filters. The filter is the roadmap — when an epic completes, the team picks up the next item in rank order. There is no fixed scope ceiling.

Vendors — close every entry point for vendor data changes

North star After R1, there is no way to change sensitive vendor data in Entrata without an auditable record.

Why this is R1

Vendor fraud is an active, escalating risk across property management. Threat actors change EINs, bank accounts, and payment terms through channels that currently leave no trail — CSV imports, NetVendor syncs, third-party integrations, and direct UI edits all bypass the activity log. When a fraudulent payment goes out, customers have no audit trail to investigate.

R4 closed the remittance door (highest-dollar attack surface). R1 closes every remaining entry point. The top 6 epics are sequenced by attack-surface risk so the most exploitable gaps close first. This is an active security gap that customers and InfoSec have flagged — not tech-debt cleanup.

This lane runs in parallel with Console. Both are R1 commitments; neither waits on the other.

Vendor Marketplace — Console APIs + VA rewrite

North star Make vendor and compliance data discoverable in Entrata Pro Console, and modernize every VendorAccess screen to the current design standard.

Why Console APIs

Entrata Pro Console is the next-generation AI assistant platform — how property managers and accounting teams will interact with Entrata data conversationally. Console uses MCP tools to read and act on data across the platform. Accounting teams are building read APIs for their domains so Console can answer questions like “which vendors have expired insurance at Oakwood?” or “show me open POs for ABC Plumbing.”

Our Vendor Directory and Vendor Compliance APIs are among the first vendor-data tools Console needs. Scope is read-only Core APIs exposing existing vendor data through a shared accounting-mcp server — no new UI, no business-logic changes. Chris Kunz’s approval-routing program (DEV-358986) depends on the same infrastructure and is already in flight. Multiple accounting teams (Corporate Accounting, Budgeting, Customer Transactions, Revenue Protection, General Accounting) are building parallel Console epics for R1 — this is org-wide.

Marketplace product work is paused (vendor enrollment, catalog) — GTM has not contracted any vendors. Direction may change after these two lanes complete; we are not planning beyond them for now.

Invoices & Invoice Processing

Invoice Processing stays focused on in-house IPS; the Invoices team leads Console APIs with SAPT readiness baked into the design.

Invoice Processing — in-house development

North star Eliminate dependency on third-party invoice processing by bringing the full IPS workflow in-house.

Every invoice that routes through a third-party processor adds cost, latency, and a failure point Entrata doesn’t control. High-volume clients feel this as delays, late payments, and AP teams chasing status. In-house IPS gives end-to-end control over throughput, accuracy, and cost per invoice. This remains the top priority for the Invoice Processing team — no change in direction from 2026.

Invoices — Console APIs + SAPT readiness

North star Make invoice and PO data discoverable in Entrata Pro Console, and ensure the PO data model is SAPT-ready so nothing breaks when that transition lands.

Why Console APIs

Same org-wide Console / MCP push as Vendors. Enables conversational questions like open POs and invoices pending approval — shared infrastructure with approval routing (DEV-358986).

Why SAPT readiness

SAPT will restructure PO/invoice storage. Per-line type fields (standard / catalog / job cost) in read responses from day one keep R1 APIs from breaking when SAPT lands.

Track 1 — Console APIs (product priority order)

  1. 1 DEV-361830 — Invoice Discovery: Search, Read and PO Match
  2. 2 DEV-361831 — Purchase Order Discovery: Search, Read and Receiving Status
  3. 3 DEV-358986 — Approval Tools: Shared Contract + Invoices and POs (in flight)
  4. 4 DEV-358985 — Admin Note on an Approval Rule (Classic prerequisite for 358986)
  5. 5 DEV-361832 — AP Spend and Commitments (R2 candidate if capacity is tight)

Track 2 — SAPT

Not a separate epic — a design constraint on the Console API work: PO read APIs include per-line type fields so the response shape survives SAPT.

Formal Invoices backlog ranking in Jira is still forthcoming (similar to the Vendor / Marketplace filters). The track order above is the current product priority.
